# スポット探索マップ（位置情報探索アプリ）

地図を動かしながら、地図の中心から半径 N km 以内のスポットを探せる Web アプリです。

- 地図の中心（＋）を基準に、半径 N km 以内のスポットを地図上のマーカーと一覧に表示します
- 検索半径はスライダーとボタンで変更できます（0.5〜50 km）
- カテゴリ（寺院・公園など）で絞り込めます。マーカーと一覧はカテゴリごとに色分けされ、絞り込みのチップが凡例を兼ねます
- 地名・住所・施設名を入力して地図を移動できます。現在地ボタン（◎）でブラウザの位置情報の場所にも移動できます（位置情報は HTTPS または localhost でのみ取得できます）
- 地図の位置・ズーム・半径・カテゴリは URL に保持され、「リンクをコピー」で同じ状態を共有できます（例：`/?lat=35.6812&lng=139.7671&z=13&r=5&c=寺院,神社`）
- 地図の中心の住所を、地図を動かしている間も約1秒ごとに更新して表示します

| 層 | 技術 |
|---|---|
| Frontend | Next.js (App Router) / TypeScript / Tailwind CSS / Leaflet |
| Backend | NestJS / TypeORM / TypeScript |
| Database | PostgreSQL + PostGIS |
| Infrastructure | Docker / Docker Compose |

## 環境構築

### 必要なもの

- Docker と Docker Compose v2.24 以降（Docker Desktop、または Docker Engine + Compose プラグイン）
- Git

Apple シリコンの Mac では、DB のイメージ（amd64 版のみ）をエミュレーションで動かすため、初回起動に時間がかかることがあります。

動作確認した環境：

- Ubuntu 24.04（GitHub Actions。push のたびに `docker compose up` からのスモークテストを実行）
- macOS 13（Apple シリコン）+ Colima

### ソースコードの取得

```bash
git clone https://github.com/daigo2895/spot-explorer.git
cd spot-explorer
```

### 環境変数（任意）

APIキーがなくても動作します。Google Geocoding API を使う場合のみ設定してください。

```bash
cp .env.example .env
# .env の GOOGLE_MAPS_API_KEY に自分のキーを設定
```

| 変数 | 説明 |
|---|---|
| `GOOGLE_MAPS_API_KEY` | 設定すると逆ジオコーディングに Google Geocoding API を使います。未設定の場合は Nominatim（OpenStreetMap）を使います |
| `NOMINATIM_USER_AGENT` | Nominatim に送る User-Agent。利用ポリシーでアプリを識別できる値が求められています |
| `NOMINATIM_BASE_URL` | Nominatim の接続先。未設定の場合は公開インスタンス（`https://nominatim.openstreetmap.org`）。自前の Nominatim を使う場合に変更します |
| `DB_USER` / `DB_PASSWORD` / `DB_NAME` | DB の接続情報。未設定の場合は `postgres` / `postgres` / `spots`（ローカル用の既定値）。DB のパスワードは初回起動時（ボリューム作成時）に反映されます |

APIキーなどの機密情報はリポジトリに含めず、`.env`（Git 管理外）で管理します。

## 実行手順

```bash
docker-compose up --build
# または docker compose up --build
```

起動後、ブラウザで http://localhost:3000 を開いてください。

起動時に次の順で自動実行されます。

1. `db`：PostgreSQL（PostGIS 拡張つき）が起動
2. `api`：マイグレーション（テーブル・インデックス作成）→ シードデータの投入 → API 起動
3. `web`：Next.js が起動

シードデータは、提供された CSV を `api/seed/spots.csv` として配置したものです（200件、列：`name, category, lat, long, address`）。シード処理は何度実行しても同じ結果になるため（後述）、再起動してもデータは重複しません。

### API

| メソッド | パス | 説明 |
|---|---|---|
| GET | `/api/spots?lat=&lng=&radiusKm=&limit=&categories=` | 中心から半径 `radiusKm` km 以内のスポットを近い順に返す。`categories`（カンマ区切り、任意）でカテゴリを絞り込む |
| GET | `/api/spots/summary` | 件数・データ全体の範囲・初期表示の中心・カテゴリごとの件数 |
| GET | `/api/geocode/reverse?lat=&lng=` | 座標から住所を返す（逆ジオコーディング） |
| GET | `/api/geocode/search?q=` | 地名・住所・施設名から候補（最大5件、名前・住所・座標・範囲）を返す。日本国内に限定 |
| GET | `/api/health` | ヘルスチェック |

アプリ全体を起動した状態で、次のスモークテストも実行できます（API の起動・半径検索・不正な入力への 400・画面の応答を確認します）。

GitHub Actions（`.github/workflows/ci.yml`）では、push のたびに api の lint・単体テスト・ビルド、結合テスト、web の lint・ビルド、まっさらな状態からの `docker compose up` とスモークテストを実行しています。

## 使用した主要ライブラリとその選定理由

| ライブラリ | 選定理由 |
|---|---|
| PostGIS | 半径検索を DB 側でインデックスを使って行うため。`geography` 型を使うと、距離をメートル単位で正確に計算できる |
| TypeORM | 課題の指定。スキーマはマイグレーションで管理し、`synchronize` は使わない |
| Leaflet / react-leaflet | APIキーなしで地図を表示でき、評価環境でもすぐに動かせるため。マーカーは `CircleMarker`（ベクター描画）にして、画像アイコンの読み込みをなくした |
| Nominatim（逆ジオコーディング） | APIキー不要で、`docker-compose up` だけで住所表示まで動くため。`GOOGLE_MAPS_API_KEY` を設定すれば Google Geocoding API に切り替えられる |
| class-validator / class-transformer | NestJS の `ValidationPipe` で、クエリの型変換と範囲チェック（緯度経度・半径の上限）を宣言的に書けるため |
| csv-parse | シードデータの CSV を、BOM や引用符を含めて正しく読み込むため |

## 実装時に特に工夫した点、および技術的な判断を行った箇所

### 1. データ設計：位置情報を `geography(Point, 4326)` で持ち、GiST インデックスを張る

- 緯度・経度を別々の数値列で持つと、半径検索のたびに全件の距離を計算することになります。`geography` 型と GiST インデックスを使い、`ST_DWithin` で絞り込むことで、インデックスを使った検索にしています
- `geometry` 型ではなく `geography` 型を選んだのは、距離を「度」ではなくメートルで扱え、半径 N km の条件をそのまま書けるためです
- 一覧の「中心からの距離」も `ST_Distance` で DB 側で計算し、近い順に並べて返しています
- 半径には上限（API側で100 km、画面では50 kmまで）を設け、極端に大きな値で全件を返すような負荷の高いリクエストを防いでいます

### 2. シード処理を冪等にする

- 各行に `source_id`（ユニーク制約）を付けて、`INSERT ... ON CONFLICT DO UPDATE` で投入しています。コンテナを再起動しても重複しません
- 提供された CSV には ID の列がないため、`source_id` は「名前・緯度・経度」から作ったハッシュ値にしています（CSV に ID 列があればそれを使います）
- 緯度・経度が不正な行はスキップしてログに出し、1行の不備で全体の起動が止まらないようにしています
- CSV の列名の揺れ（`long` / `lng` / `longitude` など）を吸収し、名前・緯度・経度以外の列は `attributes`（jsonb）に保持します

### 3. 住所取得 API の呼び出しを抑える（フロントとバックエンドの二段構え）

課題の「ユーザーが今どこを見ているかをストレスなく把握できる」と「API の呼び出し頻度を抑える」を両立させるため、次のようにしています。

**フロントエンド**（`web/src/hooks/useCenterAddress.ts`）

- 地図を動かしている間も、1秒に1回まで住所を更新します（スロットリング）。動かし終わった位置は必ず取得します
- 前回問い合わせた地点から 25 m 未満の移動では API を呼びません
- 一度取得した地点（約11 m 単位）はブラウザ内にキャッシュし、戻ってきたときは即時に表示します
- 古いリクエストの結果が、新しい表示を上書きしないようにしています

**バックエンド**（`api/src/geocoding/`）

- APIキーをブラウザに出さないため、逆ジオコーディングは必ずバックエンド経由で呼びます
- 座標を小数第4位（約11 m）で丸めてキャッシュします（件数上限・有効期限つき）。複数のユーザーが同じ場所を見た場合も、外部 API は1回で済みます
- 同じ地点への同時リクエストは、1回の外部 API 呼び出しにまとめます
- Nominatim の利用ポリシー（アプリ全体で最大1リクエスト/秒、識別できる User-Agent が必要）を守るため、呼び出しを直列にして間隔を空けています。地名検索も同じキューを通します（上限はアプリ全体にかかるため）
- 外部 API の障害時は 503 を返し、エラーはキャッシュしません（復旧後すぐに取得できるようにするため）
- Nominatim の住所は「番地, 町, 区, 都道府県, …」と逆順の要素で返るため、日本の表記（都道府県 → 市区町村 → 町名）に組み立て直しています。東京23区のように都道府県名が返らない地点は ISO 3166-2 のコードから補い、「丸の内」「丸の内一丁目」のように重なる要素は詳しい方だけを残します
- ジオコーディング（座標→住所、地名→座標）の提供元をインターフェースで切り替えられるようにし、Nominatim と Google を同じ形で扱えるようにしています

### 4. スポット検索の結果を再利用する（`web/src/hooks/useSpotSearch.ts`）

- 検索は地図の移動が止まってから行います（移動中は検索しない）。さらに 300 ms 待ってから API を呼び、連続した操作をまとめます
- 実際の検索半径の 1.5 倍の範囲を取得しておき、新しい検索範囲が取得済みの範囲に完全に含まれる場合（`前回の中心との距離 + 新しい半径 <= 前回の取得半径`）は、API を呼ばずにブラウザ側で絞り込みます。少し動かしたときや、半径を小さくしたときは API を呼びません
- カテゴリの絞り込みは API 側（SQL の条件）で行っているため、結果の再利用は取得時と同じカテゴリ選択のときだけにしています
- API から取得した直後は、PostGIS が計算した距離と並び順をそのまま表示します。結果を再利用するときだけ、新しい中心からの距離をブラウザ側で再計算します
- 新しい検索を始めたら古いリクエストは取り消し（`AbortController`）、結果が前後して表示が崩れるのを防いでいます

### 5. UI / UX

- 地図の中心に十字を表示し、住所と検索範囲（点線の円）の基準点がわかるようにしました
- 住所は地図の上部に常に表示し、取得中はスピナーを出します
- 地図の移動中・検索中は、地図の右下に状態を表示します。検索中も前の結果を残し、一覧がちらつかないようにしています
- 検索結果が0件のときは、理由と「半径を広げる」ボタンを表示します
- 一覧で選ぶとマーカーが強調されてポップアップが開き、マーカーを選ぶと一覧の該当行までスクロールします
- データは全国に散らばっているため、全体を表示すると検索範囲の円が小さすぎて操作しにくくなります。そこで、半径10 km以内に最も多くのスポットがある地点を DB で求め、初期表示の中心にしています（`/api/spots/summary`）
- スマートフォンでは、地図を上、一覧を下に表示します

### 6. 検索条件を URL に保持する（`web/src/hooks/useUrlState.ts`）

- 地図の中心・ズーム・半径・カテゴリを URL のクエリに保持し、開いたときに同じ状態を再現します。中心は小数第4位（約11 m）に丸めて URL を短くしています
- URL の更新は `history.replaceState` で行います。`pushState` だと地図を動かすたびに履歴が増えて「戻る」が使いにくくなるためです。Next.js のルーターも使わず、移動のたびにサーバー側の再描画が起きないようにしています
- 不正な値（範囲外・数値でない）は無視して既定値を使います。中心が不正なら URL 全体を無視します

## 時間が足りず実装を簡略化した箇所や、今後の改善点

課題の要件はすべて実装しています。以下は、利用者やデータが増えた場合や、運用を続ける場合に必要になると考えている改善点です。

- **キャッシュの保存先**：住所のキャッシュは API プロセスのメモリに持っています。API を複数台で動かす場合は、Redis などの共有キャッシュに置き換える必要があります
- **Nominatim の利用量**：公開インスタンスは1リクエスト/秒が上限のため、利用者が増える場合は Google など商用 API への切り替えや、自前の Nominatim の構築が必要です
- **件数が多い場合の表示**：今回は200件のため検索結果のマーカーをすべて描画していますが、件数が増える場合はマーカーのクラスタリングや、一覧のページングが必要です
- **フロントとバックエンドの距離計算の差**：再利用時のブラウザ側の距離計算は球面近似（ハバーサイン公式）のため、PostGIS（回転楕円体）の計算と境界付近でわずかに差が出る可能性があります
- **テスト**：フロントエンドのテスト（地図と一覧の連動、住所取得の間引き、検索結果の再利用など）は未実装です
- **シードデータの ID**：ID がハッシュ値のため、CSV でスポットの座標や名前を修正すると、更新ではなく別のスポットとして追加されます。CSV 側に固定の ID を持たせるのが望ましいです
- **地図タイル**：OpenStreetMap の公開タイルサーバーを使っています。利用者が多い場合は、商用のタイル配信サービスへの切り替えが必要です
- **Apple シリコンでの DB**：PostGIS プロジェクトが公開している `postgis/postgis` は amd64 版のみのため、`platform: linux/amd64` を明示してエミュレーションで動かしています。arm64 に対応したコミュニティのイメージもありますが、提出物では公開元のはっきりしたイメージを優先しました。arm64 版が公開されれば、この指定を外せます
- **開発用の構成**：docker-compose は本番に近いビルド構成のみで、ホットリロードの開発用構成は用意していません
